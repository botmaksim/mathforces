Общие требования к проектам

1. Архитектура приложения

- Приложение должно быть реализовано в виде клиент-серверной системы: серверная часть на базе userver (https://userver.tech/) (C++), клиентская – на базе Qt (C++, никакого Python).
- Клиентская часть должна быть кроссплатформенной (сборка и запуск под Windows и Linux, под macOS тоже круто было бы).
- Архитектура клиентской части должна следовать одному из паттернов – MVC (Model–View–Controller) или MVP (Model–View–Presenter) – с явным разделением ответственности между слоями:
  - Model – логика работы с данными, бизнес-правила, взаимодействие с БД и сервером;
  - View – виджеты и формы Qt, отображение данных без бизнес-логики;
  - Controller / Presenter – обработка пользовательских действий, координация Model и View.

2. Работа с базами данных

2.1. Прямой доступ к базам данных через Qt SQL (поработать ВСЕМ – даже если больно)

- В клиентском приложении должна использоваться библиотека Qt SQL для работы с локальной базой данных (SQLite или PostgreSQL в Docker).
- Локальная БД используется как кэш или автономное хранилище: кэширование справочников, настроек, журналов действий пользователя, черновиков.
- Запросы к БД должны быть инкапсулированы в классах слоя Model, исключая прямые SQL-вызовы из View и Controller/Presenter.
- Схема локальной БД должна управляться программно: создание таблиц и миграции при первом запуске.

2.2. Доступ к данным через клиент-серверное взаимодействие

- Серверная часть должна использовать PostgreSQL как основное хранилище данных; взаимодействие с СУБД осуществляется средствами userver (компонент `userver::storages::postgres`).
- Клиент обращается к серверу через HTTP REST API (формат JSON); прямой доступ клиента к серверной СУБД исключён.
- API должно поддерживать базовые операции: создание, получение, обновление, удаление записей (CRUD).
- В клиенте сетевое взаимодействие изолировано в отдельном классе-сервисе (Repository / Gateway) внутри слоя Model – View не знает об HTTP.

3. Пользовательский интерфейс

- GUI реализован на Qt Widgets (наверное, можно и Qt Quick, но лучше с обычными виджетами).
- Для отображения табличных и списочных данных обязательно использование стандартных model/view-классов Qt (`QAbstractTableModel`, QSortFilterProxyModel и др.) с привязкой к слою Model архитектурного паттерна.
- Интерфейс должен корректно отражать состояния загрузки, ошибки сети и ошибки валидации.
- Допускается использование анимаций через Qt Lottie (https://github.com/qt/qtlottie) для индикации загрузки и переходов между экранами.

4. Аутентификация и авторизация

- Серверная часть должна поддерживать аутентификацию пользователей (логин/пароль, сессионный токен или JWT).
- Разграничение прав доступа к ресурсам API (минимум две роли, например: пользователь и администратор).
- Хранение паролей — исключительно в виде хэша (bcrypt или SHA-3).

5. Требования к коду и сборке

- Система сборки — CMake (единый CMakeLists.txt для клиента и сервера или раздельные с общим корневым).
- Покрытие ключевых классов слоя Model unit-тестами (Qt Test или Google Test).
- Код должен соответствовать стилю Google Style Guide (используйте clang-format), хранится в Git-репозитории с осмысленной историей коммитов.
- Наличие README.md с инструкциями по сборке, настройке БД и запуску.
